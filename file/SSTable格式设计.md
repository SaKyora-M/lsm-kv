# SSTable 文件格式设计（v3）

> 阶段② 定下 v1 布局；阶段④-1 升级 v2（Bloom）；阶段④-2 升级 **v3（数据校验和）**：
> entry 级 CRC32 + 索引区/Bloom 区段级 CRC32，footer 从 36 字节扩到 **44 字节**，magic 改为 `b"LSM3"`。
>
> 本文档是格式的**单一真源**，代码完全照它实现；格式定错后面全返工，所以这里先想清楚，再动代码。
>
> **每一版都不向前兼容**：magic 变更是有意为之，旧文件会被明确拒绝，而不是被按新格式解析出垃圾数据。

| 版本 | magic | 关键变化 |
|---|---|---|
| v1 | `b"LSM1"` | 单数据块 + 稀疏索引 + 20 字节 footer |
| v2 | `b"LSM2"` | 新增 Bloom 区，footer 36 字节 |
| v3 | `b"LSM3"` | entry 级 CRC32 + 索引/Bloom 段级 CRC32，footer 44 字节 |

---

## 0. 设计目标与前提

### 0.1 SSTable 是什么

SSTable = **磁盘上的有序、不可变文件**。它是 MemTable 刷盘后的形态：

- **有序**：文件里的键值对按 key 升序排列（因为刷盘时 MemTable 是 `BTreeMap`，本身有序）。
- **不可变**：写完就不再修改。旧数据靠"新文件覆盖 + Compaction 清理"，而不是原地改。

### 0.2 有序带来两个好处

1. **读单个 key**：可以二分定位，不用全文件扫描；
2. **合并**：两个有序文件做归并，O(n) 就能合并。

但文件不能像内存数组那样随机按下标访问，怎么二分？**答案就是索引**——这就是本设计的核心。

### 0.3 v3 的定位

单数据块 + 稀疏索引 + **Bloom Filter** + **分段校验和** + footer。

- 仍不做 block 切分（那是比校验和更大的重构，见 §7）。
- **v3 的目标：让读路径碰到的每一个字节都被校验过。** 具体是三层：
  1. 每条 entry 自带 CRC32 → 读到哪条校验哪条；
  2. 索引区整体一个 CRC32 → 索引被改坏会直接报错，不会把二分引到错地方；
  3. Bloom 区整体一个 CRC32 → **防止坏 Bloom 造成假阴性**（把存在的 key 判成不存在 = 丢数据）。
- **不做"整表 CRC"**：它要求读完整文件才能校验，会把 v2 刚做好的"miss 路径只读 footer + Bloom"彻底废掉（见 §5.3）。

## 1. 整体字节布局

```
┌───────────────────────────────────────────────────────────┐
│ 数据区（Data Section）—— 从文件偏移 0 开始                   │
│ ┌───────────────────────────────────────────────────────┐ │
│ │ entry 1: [key_len u32][key][flags u8][value_len u32]  │ │
│ │          [value][crc32 u32]                           │ │
│ │ entry 2: ...                                          │ │
│ │ entry 3: ...                                          │ │
│ │ ...（按 key 升序）                                     │ │
│ └───────────────────────────────────────────────────────┘ │
├───────────────────────────────────────────────────────────┤
│ 索引区（Index Section）—— 整体受 footer 的 index_crc32 保护 │
│ ┌───────────────────────────────────────────────────────┐ │
│ │ entry_count u32     ← 数据区总条数                     │ │
│ │ index_count u32     ← 索引项数量                       │ │
│ │ index 1: [key_len u32][key][offset u64]               │ │
│ │ index 2: ...                                          │ │
│ │ ...（稀疏：每隔 N 条数据记一个）                        │ │
│ └───────────────────────────────────────────────────────┘ │
├───────────────────────────────────────────────────────────┤
│ Bloom 区（Bloom Section）—— 整体受 footer 的 bloom_crc32 保护│
│ ┌───────────────────────────────────────────────────────┐ │
│ │ bit array（m_bits 位，按字节对齐，无头部）               │ │
│ └───────────────────────────────────────────────────────┘ │
├───────────────────────────────────────────────────────────┤
│ Footer（固定 44 字节，文件最末尾）                          │
│ ┌───────────────────────────────────────────────────────┐ │
│ │ index_offset u64    ← 索引区起始（= 数据区结束偏移）    │ │
│ │ index_len    u64    ← 索引区字节长度                    │ │
│ │ bloom_offset u64    ← Bloom 区起始偏移                  │ │
│ │ bloom_len    u64    ← Bloom 区字节长度                  │ │
│ │ index_crc32  u32    ← 索引区整体 CRC32                  │ │
│ │ bloom_crc32  u32    ← Bloom 区整体 CRC32                │ │
│ │ magic  4 字节        ← 固定 b"LSM3"                     │ │
│ └───────────────────────────────────────────────────────┘ │
└───────────────────────────────────────────────────────────┘
```

**所有整数都用小端（little-endian）**，和 WAL 一致，跨平台。

区间关系（写路径必须满足，读路径必须校验）：

- `数据区 = [0, index_offset)`
- `索引区 = [index_offset, index_offset + index_len)`
- `Bloom 区 = [bloom_offset, bloom_offset + bloom_len)`
- 正常情况下 `bloom_offset == index_offset + index_len`（三段紧邻、无空洞）
- `Footer = [文件长度 - 44, 文件长度)`

## 2. 各字段说明

### 2.1 数据区

- 每条 entry：`[key_len u32][key][flags u8][value_len u32][value][crc32 u32]`
  - `key_len`：key 的字节长度
  - `key`：key 的原始字节
  - `flags`：1 字节标记位（见下）
  - `value_len`：value 的字节长度
  - `value`：value 的原始字节
  - `crc32`：本条 entry 的校验和（v3 新增，见下）
- **按 key 升序**写入（字节序，即 `Vec<u8>` 的字典序比较）。
- **tombstone 用 `flags` 的 bit 0 标记**：
  - `flags bit0 = 0`：正常值，`value_len` 可为 0（表示**空值**）
  - `flags bit0 = 1`：删除标记（tombstone），此时 `value_len = 0` 且无 value
- key 和 value 可以是任意字节（包括空、包括非 UTF-8）。

**`crc32` 的覆盖范围（必须严格一致，否则读写两侧算出的值永远不等）：**

```
crc32 = CRC32( data[pos .. pos + 该 entry 除 crc32 外的全部字节] )
```

即覆盖 **`key_len + key + flags + value_len + value`**，**不包含 `crc32` 自己**（自证会循环）。
落盘顺序是"先写内容、再写 crc"，所以 crc 永远在 entry 的最末尾。

> 为什么用 flags 字节，而不是"`value_len = 0` 就当 tombstone"？
> 因为 `put(k, "")`（空值）和 `delete(k)`（删除）都会落到 `value_len = 0`，二者无法区分。
> 阶段①的 WAL 靠 op 字节躲过了这个坑；但 SSTable 原本没有 op，所以必须显式加标记。
> 用 flags bit0 后：空值 = `flags=0, value_len=0`；删除 = `flags=1, value_len=0`，不再混淆。

### 2.2 索引区

- 开头两个计数：
  - `entry_count u32`：数据区一共多少条 entry（供迭代/调试用）。
  - `index_count u32`：后面有多少个索引项（读索引时据此解析）。
- 之后是 `index_count` 个索引项，每个：
  - `key_len u32` + `key`：该索引项对应数据 entry 的 **完整 key**（**不是前缀**）。二分时直接拿目标 key 与索引项的完整 key 逐字节比较。
  - `offset u64`：该数据 entry 在**文件中的绝对字节偏移**（指向它 `key_len` 字段的起始处）。
- **稀疏**：不是每条数据都建索引，而是每隔 **N** 条记一个（N = 常量，见 §5.1）。
  - 索引项覆盖数据区第 `0, N, 2N, ...` 条 entry。
  - `index_count = ceil(entry_count / N)`，写入时算好并存下来。
  - 最后一条数据 entry 一定落在最后一个索引项之后 **≤ N-1** 条内，所以从最后一个索引项顺序扫一定能覆盖到末尾。
- **整段受 `index_crc32` 保护**（v3）：写入时对这整段字节算一次 CRC32 存进 footer。

> 例：17 条数据、N=16 → 索引有 2 项（指向第 0 条和第 16 条），`index_count = ceil(17/16) = 2`。

### 2.3 Bloom 区

Bloom 区就是一段**裸位图**，没有任何头部字段——它的大小完全由 footer 里的 `bloom_len` 决定，条数 `n` 由索引区的 `entry_count` 给出。

**参数：**

| 参数 | 值 | 说明 |
|---|---|---|
| `BITS_PER_KEY` | `10` | 每个 key 分配 10 位 |
| `BLOOM_HASHES` | `7` | 每个 key 用 7 个哈希位置 |
| `m_bits` | `align8(max(64, n * BITS_PER_KEY))` | 位图总位数，**向上对齐到 8 的倍数** |
| `m_bytes` | `m_bits / 8` | 位图字节数（落盘长度） |

**为什么 `m_bits` 必须对齐到 8 的倍数（重要）：**

读侧没有 `n`，是拿 `bloom_len × 8` 反推位图总位数、再用它做取模的。如果写侧 `m_bits = n × 10` 不是 8 的倍数，落盘长度会被 `ceil` 成整字节，读侧反推出的模数就**比写侧大**（例如 `n = 513`：写侧 `m_bits = 5130`，落盘 `642` 字节，读侧 `m_bits = 642 × 8 = 5136`），同一个 key 在两侧算出不同的位下标 → **假阴性 → 把存在的 key 判成不存在 → 丢数据**。

所以写侧必须先把 `m_bits` 向上对齐到 8 的倍数，再除以 8；这样 `m_bytes × 8 == m_bits` 恒成立。

**哈希方案（双哈希 / Kirsch-Mitzenmacher）：**

用两个独立的 64 位 FNV-1a 哈希（只是初始基不同），把一次哈希扩展成 k 次：

```
h1 = fnv1a64(key, 0xcbf29ce484222325)
h2 = fnv1a64(key, 0x9e3779b97f4a7c15) | 1     // 置为奇数，避免退化
第 i 个位置 = (h1 + i * h2) mod m_bits          // i = 0..7，u64 用 wrapping 运算
置位方式：bits[pos / 8] |= 1 << (pos % 8)       // LSB 优先，读写必须一致
```

- `h2 | 1` 的原因：若 `h2 == 0`，7 个位置全退化到同一个 bit，等于只做了一次哈希。
- 这与"做 k 次独立哈希"的误判率几乎一样，但只哈希 2 次，省 CPU。

**误判率：**

10 bits/key + k=7 是理论最优点附近（`k_opt ≈ ln2 × bits/key ≈ 0.69 × 10 ≈ 6.9`），误判率约

```
(1 - e^(-kn/m))^k = (1 - e^(-0.7))^7 ≈ 0.0082 ≈ 0.8%
```

**空间成本：** 一张 4MB、约 6.5 万条的表，Bloom 约 `6.5万 × 10 / 8 = 80KB`，占文件约 **2%**。

**关键语义（Bloom 的立身之本）：**

- **绝不会有假阴性**：文件里存在的 key，`bloom_may_contain` 必然返回 `true`。
- 可能有假阳性：不存在的 key，有约 0.8% 概率返回 `true`（那就老老实实走原读路径）。

> 所以：**Bloom 说"不存在" = 一定不存在，可以直接返回 `NotFound`；Bloom 说"可能存在" = 不能确定，必须继续查。**
> 这个单向性是能拿它做优化的唯一依据。写错方向（把"可能存在"当成"存在"）会丢数据。

**整段受 `bloom_crc32` 保护**（v3）：之所以必须校验，是因为位图里**任何一位被意外置 0**，都会被当成"这个 key 一定不存在"——这正是"坏数据"里最危险的一种，它不会报错，会安静地返回错误的 `NotFound`。

### 2.4 Footer

固定 44 字节，放在文件**最末尾**。字节偏移严格如下：

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 8 | `index_offset u64` | 索引区起始偏移。**同时**等于数据区结束偏移 |
| 8 | 8 | `index_len u64` | 索引区字节长度 |
| 16 | 8 | `bloom_offset u64` | Bloom 区起始偏移 |
| 24 | 8 | `bloom_len u64` | Bloom 区字节长度 |
| 32 | 4 | `index_crc32 u32` | 索引区整体 CRC32 |
| 36 | 4 | `bloom_crc32 u32` | Bloom 区整体 CRC32 |
| 40 | 4 | `magic` | 固定 `b"LSM3"` |

读文件时：先 `seek` 到 `文件大小 - 44` 读 footer → 知道索引和 Bloom 在哪、以及它们的校验和 → 先校验 Bloom 再查 Bloom → 需要时再校验/读索引与数据。

> **footer 自身没有 CRC**。因为 CRC 字段就在 footer 里，footer 自证会陷入循环依赖。
> 它靠两样东西兜底：`magic`（4 字节固定标签，改坏了立刻被拒）+ 区间校验（偏移越界立刻被拒）。
> 一个被改坏的偏移量只要还能通过区间校验，就会指向合法区间内的某个位置——那种损坏已经超出本项目的威胁模型（我们防的是"磁盘位翻转 / 截断"，不是"蓄意构造的攻击文件"）。

## 3. 设计理由（为什么这么设计）

| 设计点 | 原因 |
|---|---|
| 数据区有序 | SSTable 的灵魂，支撑二分查找和归并合并 |
| 稀疏索引而非稠密 | 稠密索引等于把整个文件再存一遍；稀疏索引省空间，读时只多扫 ≤N 条 |
| 索引放数据后面 | 写入时顺序追加，不用预留空间、不用回填 |
| footer 放末尾、固定长度 | 读时先定位末尾，就能找到索引和 Bloom，不用扫全文件 |
| `index_offset` 兼做数据区边界 | 一个字段标定两个边界，避免额外存"数据区长度" |
| Bloom 放在索引之后、footer 之前 | 写入时顺序追加即可，不用回填；大小在写完数据、知道 `n` 之后才能确定 |
| Bloom 只存裸位图、不存参数 | 参数（`n`、`m`）可从 `entry_count` 和 `bloom_len` 推出来，少存 12 字节、少一处不一致风险 |
| `m_bits` 对齐到 8 的倍数 | 读侧靠 `bloom_len × 8` 反推模数，不对齐则读写两侧模数不等 → 假阴性丢数据 |
| 双哈希而非 k 次独立哈希 | 误判率几乎相同，但只哈希 2 次，省 CPU |
| **每条 entry 自带 CRC32** | 读到哪条校验哪条，能精确报出坏记录的偏移；不要求整文件读入 |
| **索引区/Bloom 区整段 CRC32** | 这两段不经过 entry 解码，被改坏会导致误读或**假阴性丢数据**，必须单独保护 |
| **footer 不做 CRC** | CRC 字段自身在 footer 里，自证会循环；靠 magic + 区间校验兜底 |
| **不做整表 CRC** | 必须读完整文件才能校验，会废掉 miss 路径的 I/O 优化（见 §5.3） |
| magic 校验 | 防止把损坏的/非 SSTable 文件当成合法表；v3 顺带挡住 v1/v2 旧文件 |
| 整数全用小端 | 和 WAL 一致，跨平台 |
| flags 字节标记 tombstone | 区分"空值"（flags=0, value_len=0）与"删除"（flags=1, value_len=0），二者都可能写成 value_len=0 |

## 4. 读一个 key 的完整流程（含不存在的 key）

假设要读 key `k`：

1. **定位 footer**：取文件长度 `len`；若 `len < 44` → 报 `Corruption`。`seek` 到 `len - 44`，读 44 字节。
2. **解析 footer**：读出 `index_offset`、`index_len`、`bloom_offset`、`bloom_len`、`index_crc32`、`bloom_crc32`、`magic`；校验 `magic == b"LSM3"`，并校验
   - `index_offset + index_len <= len - 44`
   - `bloom_offset + bloom_len <= len - 44`
   （都用带溢出检查的加法，避免整数回绕绕过校验。）
3. **读 Bloom**：`seek` 到 `bloom_offset`，读 `bloom_len` 字节。**若 `bloom_len == 0` 视为"没有 Bloom"，跳到第 5 步**（不能当成"一定不存在"，否则丢数据）。
4. **校验 Bloom 段 CRC（必须在第 5 步之前）**：`crc32(bloom 字节) != bloom_crc32` → 立刻报 `Corruption`。
   **顺序绝对不能反**：坏 Bloom 会给出错误的"不存在"，那是静默丢数据；先校验再使用，坏文件就变成显式报错。
5. **Bloom 判定**：`bloom_may_contain(位图, k)` 返回 `false` → **断定 k 不在本文件，直接返回 `NotFound`**。这一步不读索引区、也不读数据区，是本格式最省的那一次 I/O。
6. **读索引**：`seek` 到 `index_offset`，读 `index_len` 字节。
7. **校验索引段 CRC**：`crc32(索引字节) != index_crc32` → 报 `Corruption`。然后解析出 `entry_count`、`index_count` 和 `index_count` 个索引项。
8. **二分索引**：在索引项的 key 里找"**最后一个 key ≤ k 的索引项**"。
   - 若 `k` 比第一个索引项的 key 还小 → `k` 比全文件最小 key 还小 → **不存在，返回 `NotFound`**。
9. **顺序扫描数据窗口**：只读 `[offset, index_offset)` 这一段（最多 `SPARSE_INDEX_INTERVAL` 条 entry），
   从 `offset` 开始一条条解 entry（**包含** `offset` 指向的那条 entry 本身——它是本次扫描的第一条，所以是"先比这一条，再往后"）：
   - 每读一条，**先校验该 entry 的 `crc32`**：不一致 → 报 `Corruption`（错误信息里带上偏移）。
   - `entry.key == k`：命中。看 flags：bit0 = 1 → 返回 `Tombstone`；bit0 = 0 → 返回 `Found(value)`（**含空值**）。
   - `entry.key > k`：**因为数据有序，后面只会更大，可以立刻断定 k 不存在**，返回 `NotFound`。
   - `entry.key < k`：继续读下一条。
10. **扫到数据区末尾（`index_offset`）还没遇到 `key ≥ k`** → `NotFound`。

**关键洞察 1**：第 9 步"`entry.key > k` 就提前停"正是"有序"带来的——它把"全文件扫描"变成"最多扫 N 条"。

**关键洞察 2**：一次 `get` 在多层表上要查 N 张表，其中大多数是"不在"。第 5 步让这些情况只花"读 footer + 读 Bloom"（几 KB 量级），而不是"读整张表"（MB 量级）。

**关键洞察 3**：校验和是"读多少验多少"，不是"读之前先整表验一遍"——所以它不会破坏上面两条优化。

> **实现状态**：以上流程已全部落地（`src/sstable.rs::get`）。`get` 不读整个文件，只读四段：
> footer(44B) → Bloom 区 → 索引段 → 命中那一段窗口 `[offset, index_offset)`。
> 读到的总字节数与文件大小无关。实测命中路径从 189µs 降到 122µs
> （Windows / 5000 条 / criterion），8 线程并发读吞吐翻倍。

## 5. 关键问题分析

### 5.1 稀疏索引间隔 N 定多少？

**定 N = 16**（做成代码常量 `SPARSE_INDEX_INTERVAL`，可调）。

理由（空间 vs 时间的权衡）：

- 4MB 数据、平均每条 entry 约 64 字节（key 28 + value 28 + 8 字节长度头），约 6.5 万条。
- `N=16` → 索引约 4100 项，每项约 40 字节（4 + key 28 + offset 8）→ 索引约 **160KB**，相对 4MB 数据约 4%，可忽略。
- 二分定位后，最多顺序扫 **16 条 ≈ 1KB**，很快。
- `N` 越大 → 索引越小、但要扫越多；`N` 越小 → 反之。16 是一个两边都不极端的折中。

> 这不是唯一正确答案。做基准测试时可以拿不同 N 对比实测，再调。

### 5.2 为什么是 10 bits/key、7 个哈希？

- 误判率由 `bits/key` 和 `k` 共同决定，公式 `(1 - e^(-kn/m))^k`。
- `bits/key` 每 +1.44，误判率大约降 10 倍；但空间线性增长。
- 10 bits/key（≈0.8%）是"空间只占文件 2%、误判率已经很低"的常见折中；LevelDB/RocksDB 默认也是 10。
- `k` 取理论最优 `ln2 × 10 ≈ 6.9`，取整为 **7**。
- 调参注意：`k` 和 `bits/key` 要一起改，单独改 `k` 反而会变差。

### 5.3 校验和为什么是"entry 级 + 段级"，而不是整表级？

四种可选粒度，逐一对比：

| 粒度 | 覆盖 | 读时能否验证 | 问题 |
|---|---|---|---|
| **entry 级**（选用） | 每条记录 | ✅ 读到哪条验哪条 | 每条多 4 字节（约 6% 开销） |
| **段级**（选用） | 索引区、Bloom 区各一段 | ✅ 读完该段立刻验 | 只能定位到"段"，不能定位到字节 |
| 整表级 | 整个文件 | ❌ 必须读完整文件 | 与 miss 路径优化冲突 |
| 块级 4KB | 每 4KB 一块 | ✅ 读到哪块验哪块 | 需要先有"分块"格式，重构量大 |

**为什么不用整表 CRC：**

1. **它会毁掉 v2 的收益**：一次 miss 本来只读 footer（44B）+ Bloom（几 KB），加了整表 CRC 就得把整张表读完才能验证——N 张表的 miss 变成 N 次全表读。
2. 它只能回答"整个文件有没有坏"，不能回答"坏在哪条记录"，错误定位能力反而更差。
3. 一条记录坏了就得判整个文件作废，粒度太粗。

**为什么索引区和 Bloom 区还要单独加段级 CRC：**

因为它们**不经过 entry 解码**，entry 级 CRC 保护不到：

- 索引区被改坏 → 二分拿到错误的 `offset` → 读到错位的 entry，或者跳过本该命中的 entry → **返回错值或漏值，而且不该报的错不会报**。
- Bloom 区被改坏 → 某些位被清零 → 假阴性 → **把存在的 key 判定为不存在 → 直接丢数据**。
- 这两种损坏都不会让 entry 的 CRC 失败（坏的字节根本不在 entry 里），所以必须各配一个段级 CRC。

**为什么 footer 不做 CRC：** 见 §2.4。CRC 字段在 footer 里，自证循环；靠 magic + 区间校验兜底。

**为什么不是块级（4KB）CRC：** 见 §5.4。

### 5.4 entry 级 CRC 的开销，以及将来为什么该换块级

- **空间**：每条 entry 多 4 字节。平均 entry 约 64 字节 → 约 **6%** 膨胀；一张 4MB 的表约多 250KB。
- **CPU**：`crc32fast` 有硬件加速（SSE4.2 / PCLMULQDQ），每条几十字节的 CRC 开销远小于一次系统调用。
- **真实 LSM 的做法**：LevelDB/RocksDB 用 **4KB 块 + 每块一个 4 字节 CRC**，把开销从"每条 4 字节"摊薄到"每 4KB 4 字节"（约 0.1%）。代价是必须先引入"块"这一层（块索引、块内定位、块边界可以切在 entry 中间）。
- **本项目的取舍**：当前是"单数据块"格式，entry 级 CRC 是与它匹配的**最小完整方案**，语义也更强（能精确报出坏的是哪条）。等真要做块级 I/O 时，再把这些 4 字节从 entry 挪到块尾，magic 升 `LSM4` 即可。

### 5.5 空 SSTable（数据区 0 条 entry）还成立吗？

**格式上成立**：`entry_count = 0` → `index_count = 0`，索引区只有 8 字节（两个 0，CRC 为这 8 字节的 crc32）；`n = 0` → `m_bits = max(64, 0) = 64` → Bloom 8 字节（全 0）；footer 照旧 44 字节。所有字段都能自洽解析。

**但写路径不会产生它**：刷盘只在 MemTable 大小 ≥ 阈值（4MB）时触发，此时至少有一条记录。

结论：**读路径要能容忍 `entry_count = 0`（防御性解析），写路径保证不生成空表。** 这叫做"防御式读、约束式写"。

> 附注：若一个 MemTable 里全是 tombstone（如 `put(k,v)` 后又 `delete(k)`），也会照常刷盘，产出一个"全是 tombstone entry（`flags bit0=1`）"的 SSTable。语义正确（读这些 key 返回 `NotFound`/`Tombstone`），只是有点浪费，暂不做特殊优化。

### 5.6 怎么判断读到了"数据区末尾"？

**用 `index_offset`，而不是文件总长度。**

- 数据区末尾 = 索引区起始 = footer 里的 `index_offset`。
- 文件末尾是 footer，**不是**数据区末尾——所以扫描数据区时，边界是 `index_offset`。
- 实现上：维护"剩余数据字节数 = `index_offset - 当前偏移`"，归零即到数据区末尾。
- **前提**：`index_offset` 必须**先由 footer 读出**（见 §4 第 1 步），再开始扫数据区；不能"边扫数据、边等 footer"。§4 的流程顺序（先读 footer）正是为此。
- 同理，`read_all`（全表顺序读）的扫描右边界也是 `index_offset`，不是文件长度——Bloom 区在索引区之后，不能被当成 entry 解出来。

### 5.7 magic 的端序坑（重要）

`magic = 0x4C534D31 即 "LSM1"` 这种写法**有坑**：`0x4C534D31` 若按小端 `to_le_bytes()` 写盘，落盘字节是 `[31 4D 53 4C]` = **"1MSL"**，不是 "LSM1"。

**解决办法：magic 不当整数，当"4 字节标签"**：

```rust
const MAGIC: &[u8; 4] = b"LSM3";   // 直接写这 4 个字节，不涉及端序
```

本质：magic 是**标识符**，不是**数字**。用字节标签既能让 hexdump 里看到 "LSM3"，又绕开端序纠结。

> v3 顺带把 magic 升级成 `LSM3`：旧 v1/v2 文件读到会被明确拒绝，而不是被按 v3 解析出垃圾数据。这比"静默误读"安全得多。entry 布局变了（多了 4 字节 crc32），所以这个版本号是**必须**升的。

### 5.8 读索引时怎么知道有几个索引项？

索引区开头存了 **`index_count`**（索引项数量），读的时候直接读它，不依赖 N 常量。

- 为什么存 `index_count` 而不是只存 `entry_count`：`index_count = ceil(entry_count / N)` 本可推导，但显式存下能让索引区**自描述**——将来 N 变了、或加版本时，旧文件仍能正确解析。
- 代价仅 4 字节，换来鲁棒性，值得。

### 5.9 Bloom 区为什么不存参数（n、k、bits/key）？

- `n` 已经由索引区的 `entry_count` 给出；
- `m` 由 footer 的 `bloom_len × 8` 给出；
- `k` 是全局常量 `BLOOM_HASHES`，所有文件一致。

参数冗余存储只会带来"两处不一致"的风险。若将来要支持**每个文件不同的 Bloom 参数**，再在 Bloom 区头部加版本字节也不迟——但那属于格式 v4 的事。

## 6. 与 WAL 的对比

| | WAL | SSTable |
|---|---|---|
| 写入方式 | 追加，可重复 key | 一次成型，key 唯一 |
| 是否有序 | 按写入顺序 | 按 key 升序 |
| 是否有索引 | 无 | 有（稀疏索引） |
| 是否有 Bloom | 无 | 有（v2 新增） |
| 是否可变 | 一直追加 | 写完不可变 |
| 是否有校验 | 每条记录 CRC32 | **每条 entry CRC32 + 索引/Bloom 段级 CRC32（v3）** |
| 用途 | 崩溃恢复 | 持久存储 |

## 7. 后续演进预留（现在不做）

- **分块（block）**：数据区分成多个 block + block 级索引，便于局部加载（LevelDB 的做法）。
- **块级校验和**：把 4 字节 CRC 从"每条 entry"挪到"每 4KB 块"，把校验开销从 ~6% 摊薄到 ~0.1%（见 §5.4）。
- **Bloom 参数按文件自适应**：目前固定 10 bits/key，若某些表 key 特别多可动态调整。
- **版本号字段化**：在 footer 里加显式 `version u16`，让 magic 只承担"是不是 SSTable"的职责。

## 9. 版本变更记录

### v3（阶段④-2，数据校验和）

| 项 | v2 | v3 |
|---|---|---|
| magic | `b"LSM2"` | `b"LSM3"` |
| entry 布局 | `[key_len][key][flags][value_len][value]` | 末尾追加 `crc32 u32` |
| footer | 36 字节（4 × u64 + magic） | 44 字节（4 × u64 + 2 × u32 + magic） |
| 校验力度 | 仅 magic | entry 级 CRC32 + 索引段 CRC32 + Bloom 段 CRC32 |
| 兼容性 | — | **不兼容 v2**，旧 `.sst` 会被 magic 校验拒绝 |

### v2（阶段④-1，Bloom Filter）

| 项 | v1 | v2 |
|---|---|---|
| magic | `b"LSM1"` | `b"LSM2"` |

单数据块 + 稀疏索引（N=16）+ 20 字节 footer + flags 字节标记 tombstone。
