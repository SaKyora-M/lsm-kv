## 一、项目定位

用 Rust 从零实现的**嵌入式键值存储引擎**，核心数据结构是 LSM-Tree。

目标不是"能跑就行"，而是把 LSM 的几个核心机制真正做对：

- 写入路径的持久化与崩溃恢复
- 磁盘格式（有序、不可变、带校验）
- 读放大的抑制（Bloom Filter + 稀疏索引）
- 写放大的代价与合并
- 并发读写的正确性

**明确不做**：分布式、事务/MVCC、压缩、生产级调优。见第六节。

## 三、关键设计决策

> 这一节是整份文档最重要的部分。改代码之前先读完。

### 3.1 删除必须写墓碑，不能物理删除

磁盘上的 SSTable 是**不可变**的，旧值永远还在文件里。删除只能"在上层写一个
`None` 标记"，读的时候看到墓碑就停，不再往更旧的表找。

由此推出两条铁律：

1. **读到墓碑必须停**。继续往更旧的表找，会读到本该被删掉的旧值。
2. **墓碑不能随便丢**。只有"全量合并"（把所有表合成一张）之后才可以丢，
   因为那时底下不再有任何更老的数据。改成 leveled compaction 后这条就不成立了，
   非最底层的墓碑必须保留。

### 3.2 写路径的顺序不能反

```
put: 拿 memtable 写锁 ──► WAL 追加 ──► 改 MemTable ──► 释放
```

**先写 WAL，再改内存**。反过来（先改内存再写 WAL）如果中间崩溃，数据只在内存里，
重启就没了。

**memtable 写锁必须包住这两步**。这是并发下的关键：flush 要改 memtable 就得先拿这把锁，
所以它不可能插到"WAL 写完、内存还没改"的中间，也就不会出现"WAL 被截断但记录只活在内存里"
的丢失。（早期版本把两把锁分开拿，就是这个 bug。）

### 3.3 锁顺序与并发模型

```
memtable → sstables → wal
```

前缀原则：拿了后面的锁，就不能再回头拿前面的。`parking_lot` 的 `Mutex` 和 `RwLock`
**都不可重入**——同一线程重复拿锁、或持读锁时再拿写锁，都会死锁。

| 方法 | 持有的锁 |
|---|---|
| `flush` | memtable(w) → sstables(w) → wal |
| `compact` | memtable(w) → sstables(w) |
| `put` / `delete` / `put_batch` | 临界区内 memtable(w) → wal |
| `get` | memtable(r) 释放后 → sstables(r) |
| `maybe_compact` | sstables(r)，释放后才调 compact |

**读路径两把锁不嵌套**，所以多个读线程完全并行——这是阶段④换 `RwLock` 的全部收益。

### 3.4 flush 的读可见性（容易改坏）

`flush` 里 memtable 写锁要持有到函数结束。局部变量按**声明的逆序**析构，所以
`sstables` 写锁先释放、`memtable` 写锁后释放。这保证读者要么看到"旧 memtable + 旧 metas"，
要么看到"空 memtable + 新 metas"。

如果哪天把这两个 guard 的释放顺序调换（或者提前 `drop` 了 memtable），就会出现
"memtable 已清空、新表还没登记"的窗口 —— 读者查不到 key，**静默返回 `None`**，
而且没有任何报错。`concurrent_readers_and_writers` 测试专门盯着这个。

### 3.5 compaction 的崩溃安全

顺序必须是：

```
① 写新表成功 ──► ② 改内存 metas ──► ③ 删旧文件
```

任一时刻崩溃：

- ① 之前：什么都没变，重开读旧表，正确
- ① 后 ② 前：新表在磁盘但没登记，旧表还在；重开扫到全部，按 id 新覆盖旧，正确
- ② 后 ③ 前：内存已换成 [新表]，磁盘上冗余；重开同样正确
- ③ 之后：干净

即"最坏只留冗余文件，绝不丢数据"。**不要**为了省事改成"先改内存再写表"。

### 3.6 SSTable 格式与校验和

完整说明见 [`SSTable格式设计.md`](SSTable格式设计.md)。这里只列最容易被改错的点：

- **Bloom 的位数必须向上对齐到 8 的倍数**。读侧用 `bloom_len * 8` 反推模数，
  写侧不对齐就会两边取模不一致 → 假阴性 → 丢数据。
- **必须先校验 Bloom 段的 CRC，再使用 Bloom 结果**。坏 Bloom 会给出"不存在"，
  那是静默丢数据；先校验就变成显式 `Corruption`。
- **entry 的 CRC 覆盖 `key_len..value`，不含 CRC 自己**（自证会循环）。
- **magic 按字节比较，不要读成整数**（端序坑，见格式文档 §5.7）。

### 3.7 为什么单条 put 不做 WAL 缓冲

基准显示单条 `put` 的 6.4µs 几乎全花在一次 `write_all` 系统调用上。很自然会想到加
`BufWriter`——但**不能加**：

现在每条写返回后，记录已经在操作系统缓存里，**进程崩溃不丢**（掉电会丢，因为本来就没 fsync）。
加了用户态缓冲，记录留在进程内存里，进程一崩就没了。这是对用户不可见的静默降级，
等于把 WAL 的意义砍一半。

要摊薄系统调用，正确做法是**批量写**：`Db::put_batch` 把一整批编码进一个缓冲区、
一次 `write_all` 落盘。实测单条摊销从 6.36µs 降到 0.30µs（21×），
且崩溃语义只是从"逐条持久"变成"前缀持久"（每条记录仍有独立长度和 CRC，
`replay` 在残缺处停下），没有丢掉"进程崩溃不丢"这一层。

## 五、性能数据

Windows / 16 核 / criterion，5000 条数据（value ~75B）：

| 操作 | 耗时 |
|---|---|
| `put` 单条 | 6.36 µs |
| `put_batch` 100 条 | 0.30 µs/条 |
| `get` 命中 memtable | 207 ns |
| `get` 命中 SSTable | 122 µs |
| `get` 未命中 SSTable | 71.9 µs |
| `compact` 4×1000 | 12.3 ms |

并发读 memtable：1/2/4/8 线程 → 4.10 / 7.34 / 12.94 / 17.45 M 次每秒（8 线程 4.25×）。

**注意**：SSTable 路径在 Windows 上被 `open`/`read` 系统调用主导（约 70µs 是固定开销），
Linux 上会低不少。这些数字用于**横向对比**（改前 vs 改后），不要当作绝对性能承诺。

复现：`cargo bench`。

## 六、已知限制

| 限制 | 影响 | 想改的话 |
|---|---|---|
| 全量 compaction | 写放大 = 数据总量，数据大了很痛 | 需要 leveled/tiered 分级 |
| compaction 同步执行 | 合并期间读写全部阻塞 | 需要后台线程 + `Arc<Db>` |
| 单数据块 | 没有块级索引，没有压缩 | 数据区切块 + 块内索引 |
| 无范围扫描 | 只能点查 | `Db::scan(range)`，内部 `read_all` 已有雏形 |
| 无 fsync 策略 | 掉电可能丢最近写入 | 加 `SyncPolicy` 枚举 |
| 无 MVCC/快照 | 读不到历史版本 | 版本号 + 快照列表 |
